## 1. 배경 · 문제

### 풀려던 문제
기존 습관 앱들은 **"더 많이 추적할수록 좋다"** 는 전제 위에 만들어져 있다. 무제한 습관, 촘촘한 통계, 복잡한 설정. 그 결과 역설적으로:

1. **추적 항목이 많아 관리 자체가 일이 된다** → 며칠 만에 앱을 닫는다.
2. **스트릭(연속기록)이 하루 빠지면 0으로 리셋** → "어차피 깨졌으니" 하며 완전히 이탈한다. (실제로 행동과학 연구에서 하루 거른 것은 습관 형성에 거의 영향이 없는데도, 앱이 0으로 만들어 죄책감을 준다.)
3. **설정과 옵션이 많아 진입 장벽이 높다.**

### 기존 대안이 부족했던 점
- **Habitica / Streaks / Productive 등**: 기능이 풍부하지만 그게 곧 부담. "또 하나의 관리 대상"이 된다.
- **대부분의 트래커**: 하드 스트릭(hard streak) — 하루만 빠져도 기록이 무너지는 구조가 이탈을 가속한다.

### 가설
> 제약이 곧 가치다. **추적을 3개로 강제로 줄이고**, **하루쯤은 봐주는** 트래커라면, "지키기 쉬워서 계속 쓰는" 앱이 된다.

이 가설을 흔들지 않기 위해 프로젝트 시작 시 **10개 조항의 "헌법"(CLAUDE.md)** 을 먼저 작성했다. 1조가 "3개 제약은 신성불가침", 2조가 "5초 안에 끝나지 않으면 만들지 않는다". 모든 기능 결정은 이 헌법을 상위 기준으로 통과해야 했다.

## 2. 핵심 의사결정 (Top 3)

### 결정 ① 습관 개수를 3개로 "강제"할 것인가 — 제품 정체성의 핵심

- **선택지**
  - (A) 무제한 + "3개를 권장"하는 소프트 가이드
  - (B) Free 3개 / Pro 무제한 (업셀 동력으로 활용)
  - (C) **누구에게도 3개를 넘기지 않는 하드 제약**
- **선택: (C)**. 헌법 1조로 못박았다. "3개 제약"은 기능 제한이 아니라 **유일한 차별점이자 가치 제안**이기 때문. 여기가 흔들리면 "또 하나의 습관 트래커"가 된다.
- **버린 이유 (트레이드오프)**
  - (A)는 결국 사용자가 10개를 등록하고 똑같이 지친다 — 우리가 풀려던 문제를 스스로 재현.
  - (B)는 "무제한"을 돈 받고 파는 순간, 제품 철학("적게가 낫다")과 정면충돌. 수익을 위해 정체성을 파는 셈.
  - 트레이드오프로 **"파워유저 이탈"과 "업셀 매출 포기"를 감수**. 대신 제품 메시지가 칼처럼 선명해졌다.

### 결정 ② 연속기록을 "관용적(Forgiving)"으로 만들 것인가 — 이탈 방어의 핵심

- **선택지**
  - (A) 전통적 하드 스트릭 (하루 빠지면 0)
  - (B) **Two-Day Rule** — 하루 빠짐은 "쉼표(Pause)"로 보고 흐름 유지, 이틀 연속이어야 리셋
  - (C) 빠진 날을 소급 체크로 메우게 허용
- **선택: (B)**. "흐름(Flow)"이라는 자체 개념으로 재정의. 하루는 봐주되, 이틀 연속은 끊는다.
- **버린 이유**
  - (A)는 바로 그 이탈 트리거 — 우리가 없애려던 죄책감의 근원.
  - (C)는 헌법 2조(5초)·데이터 무결성과 충돌. "과거를 고칠 수 있다"는 순간 "습관은 오늘을 사는 것"이라는 정신이 무너지고, 캘린더 편집 UI가 붙어 5초를 넘긴다. → **과거는 read-only로 확정**.
  - 트레이드오프: "하루는 봐준다"가 자칫 느슨함으로 읽힐 위험. 그래서 **이틀째는 단호하게 끊어** 긴장을 유지했다.

### 결정 ③ 백엔드를 둘 것인가 — 운영 지속가능성의 핵심

- **선택지**
  - (A) Supabase로 계정·클라우드 동기화
  - (B) **완전 로컬 퍼스트 (서버 0대, 계정 없음)**
- **선택: (B)**. 헌법 5조 "직접 관리하는 서버를 운영하지 않는다". 실제 코드에 **네트워크 호출 0개, Supabase import 0개**.
- **버린 이유**
  - 1인 개발에서 **서버 운영 부담은 사이드 프로젝트를 죽이는 가장 큰 원인**. 유지비·장애대응·인증보안이 전부 부채가 된다.
  - 트레이드오프: 기기 간 동기화·백업을 포기. 대신 "서버 없음 · 계정 없음 · 수집 없음"이 **프라이버시 마케팅 메시지이자 $0 운영비**로 되돌아왔다. Play 데이터 보안 신고서도 "데이터 수집 안 함"으로 가장 강한 신뢰 신호가 된다.

## 3. 기술적 난관 (자랑할 만한 구현)

### 난관 ① iOS 위젯 ↔ RN 앱 데이터 동기화 (App Group)

RN(JS) 세계와 Swift WidgetKit은 메모리를 공유하지 않는다. 위젯이 항상 최신 체크 상태를 보여주려면 **프로세스 경계를 넘는 공유 저장소**가 필요했다.

- **App Group** `group.com.qlemql.minimalhabittracker` 를 RN 앱과 위젯 익스텐션 양쪽 entitlement에 등록.
- **자체 Expo 네이티브 모듈(`shared-defaults`)** 을 작성해 JS → `UserDefaults(suiteName:)` 쓰기를 브릿지. 값을 쓰는 즉시 `WidgetCenter.reloadAllTimelines()` 를 호출해 위젯을 갱신한다.

```swift
// modules/shared-defaults/ios/SharedDefaultsModule.swift
private let suiteName = "group.com.qlemql.minimalhabittracker"
// setItem → UserDefaults(suiteName:).set(...) 직후
WidgetCenter.shared.reloadAllTimelines()
```

- **타이밍 문제 해결**: "오늘"의 경계(자정)에 위젯이 stale해지는 문제는, 타임라인 정책을 `.after(다음날 자정)` 으로 설정해 **시스템이 자정에 자동으로 새 엔트리를 요청**하게 만들어 해결.

```swift
let tomorrow = calendar.startOfDay(for: calendar.date(byAdding:.day, value:1, to: now)!)
let timeline = Timeline(entries: [entry], policy: .after(tomorrow))
```

- **결과**: iOS 위젯 **5종**(홈 Small/Medium + 잠금화면 accessoryCircular/Rectangular/Inline)을 단일 데이터 소스로 구동. Android는 Kotlin RemoteViews + SharedPreferences + AlarmManager(자정 broadcast)로 동일 패턴을 재현했고, 위젯 탭으로 **앱을 안 열고도** 낙관적 토글 후 포그라운드 진입 시 동기화하도록 큐잉했다.

### 난관 ② 알림 v2 — "완료한 날엔 알림이 안 오게"

본인 피드백에서 출발: *"이미 체크한 날에도 리마인더가 와서 거슬린다."* 그런데 RN은 백그라운드에서 발사 직전에 JS 로직(완료 여부 판단)을 돌릴 수 없다. 서버 푸시도 헌법 5조로 금지.

- **해법**: DAILY 반복 트리거를 버리고, **앞으로 7일치를 개별 single-shot 캘린더 알림으로 미리 등록**(`REMINDER_DAYS_AHEAD = 7`). 각 알림 데이터에 `date: 'YYYY-MM-DD'` 를 심는다.
- 습관을 완료하면 **그날 날짜에 매칭되는 알림 1개만 취소** — 내일 이후와 복귀 알림은 그대로.

```ts
// 완료 시: 오늘 것만 콕 집어 취소
if (data?.habitId === habitId && data?.kind === 'reminder' && data?.date === today) {
  await Notifications.cancelScheduledNotificationAsync(notification.identifier);
}
```

- **복귀 유도**: 7일치 뒤에 `kind: 'reactivation'` 알림 1개를 더 걸어, **일주일간 미사용 시 부드러운 복귀 알림**("🌱 일주일 만이에요")이 뜨게 함.
- **앱 실행 시 idempotent 보충**: 모든 알림을 지우고 재등록하는 `refreshHabitReminders()` 를 콜드 스타트에 호출 → 며칠 만에 열어도 항상 7일 윈도우가 채워진다. 여러 번 호출돼도 중복이 안 생긴다.
- **결과**: 서버 한 대 없이, "이미 한 일은 조르지 않고 / 잊으면 한 번만 부른다"는 알림 UX를 순수 로컬로 구현.

### 난관 ③ "끊기지 않는" 흐름 계산 (Two-Day Rule)

저장된 카운터를 증감하면 시간여행 버그(날짜 조작, 미들나잇 경계)가 생긴다. 그래서 **흐름을 저장하지 않고 로그에서 매번 역산**한다.

```ts
// src/utils/streak.ts — 오늘부터 과거로 최대 365일 역방향 순회
if (completedDates.has(dateStr)) { flowDays++; consecutiveMisses = 0; }
else {
  consecutiveMisses++;
  if (consecutiveMisses >= 2) break;   // 이틀 연속 빠짐 = 흐름 종료
  if (i === 0) isBreathingToday = true; // 오늘만 빠졌으면 '쉼표' 상태
}
```

- `currentFlowDays`(현재 흐름)와 `longestFlow`(역대 최장)를 분리. 졸업 자격은 "한 번이라도 도달한 최장 단계" 기준이라, 흐름이 잠깐 끊겨도 키운 보람이 사라지지 않는다.
- 단일 함수가 흐름 일수·시작일·쉼표 여부·상태(`new`/`breathing`/`active`)를 한 번에 반환 → 카드 UI, 성장 단계, 졸업 판정이 전부 같은 진실 소스를 쓴다.

## 4. 의도적으로 안 한 것 (1인 개발 범위 절단)

헌법 3조("추가하기 전에 먼저 뺄 것을 찾아라")와 10조("이 기능이 기존 앱과 뭐가 다른가에 답 못하면 실행 안 함")가 강제 게이트 역할을 했다.

| 안 한 것 | 이유 |
|---|---|
| **무제한 습관 / Pro 업셀로서의 개수 해제** | 헌법 1조. 정체성을 돈으로 파는 것 |
| **클라우드 동기화 · 계정 · 로그인** | 헌법 5조. 서버 부담 = 사이드 프로젝트 사망 원인 |
| **분석/추적 SDK (Firebase·Amplitude 등)** | 프라이버시 우선 + "수집 없음" 메시지. 대가로 **사용자 지표를 스스로 못 봄** |
| **과거 날짜 소급 체크** | 5초 룰·데이터 무결성·"오늘을 사는 것" 철학과 충돌 → 과거 read-only 확정 |
| **구독(월정액) 모델** | 헌법 7조. 1회 결제 + 기능팩으로만 |
| **설정 화면 비대화** | 헌법 6조. 설정은 알림 시간·테마 2종까지만. "우리가 대신 결정"이 배려 |
| **iOS/Android 동시 완벽 대응** | 헌법 9조. iOS로 코어 검증 먼저, Android는 졸업하듯 뒤따라감 |
| **퇴행 로직·21일 중간 단계·100/365일 엔드게임** | 복잡도 축소. 추후 재논의로 보류 |

> 핵심은 "못 만든 것"이 아니라 **"안 만들기로 매번 명시적으로 결정한 것"**. 범위 확장을 막는 메커니즘(헌법)을 코드보다 먼저 만든 것이 11주에 7릴리즈를 가능케 했다.

## 6. 회고

### 잘한 것
- **"코드보다 헌법을 먼저"**: 10개 조항을 못박은 게 11주 7릴리즈의 진짜 원동력. 모든 기능 토론이 "헌법 몇 조에 걸리나"로 5초 안에 끝났다.
- **제약을 제품으로**: 3개 제한과 관용적 흐름은 "못 하는 것"이 아니라 "이게 우리다"가 됐다.
- **로컬 퍼스트의 복리**: 한 번의 결정($0 서버)이 비용·프라이버시·마케팅 메시지·심사 신고서까지 동시에 해결.

### 다시 한다면 바꿀 것
- **프라이버시 보존형 최소 지표라도 둘 걸**: 다운로드/리텐션을 전혀 못 보니 "본인 사용"이라는 정성 신호에만 의존했다. 온디바이스 집계 후 익명 카운터 정도는 "수집 없음" 원칙과 양립 가능했을 것.
- **Android를 더 일찍 동등화**: iOS 우선이 맞았지만, App Group/RemoteViews 동기화 패턴을 처음부터 양 플랫폼 공통으로 추상화했다면 위젯 재구현 비용이 줄었을 것.
- **결제(IAP) 골격을 더 일찍**: proStore를 stub으로만 둔 채 미뤄, 수익화 검증이 계속 뒤로 밀렸다.

### 배운 것
> 1인 개발에서 가장 비싼 자원은 시간이 아니라 **"아니오"라고 말하는 규율**이다.
> 기능을 더하는 일은 쉽고, 더하지 않기로 매번 결정하는 일은 어렵다. 그 결정을 사람의 의지가 아니라 **문서화된 제약**에 위임한 것이 이 프로젝트의 진짜 아키텍처였다.

## 부록: 심화 Q&A

### Q1. "3개 제약"을 코드·UX에서 어떻게 강제했나? 반발/이탈은?

**3중 방어**로 어떤 경로로도 4번째 습관이 생기지 않게 했다.

1. **상수 + 스토어 가드** (`src/store/habitStore.ts`)
   ```ts
   const MAX_FREE_HABITS = 3;
   canAddHabit: () => habits.filter(h => !h.isGraduated).length < MAX_FREE_HABITS,
   addHabit: (...) => { if (!get().canAddHabit()) return null; /* 추가 거부 */ }
   ```
   - 핵심: **졸업한 습관은 카운트에서 제외**(`!isGraduated`) — "3개를 끝까지 키우면 비우고 새로 시작"이라는 순환을 허용.
2. **UI 게이트** (`app/index.tsx`): 3개가 차면 "추가" 버튼이 사라지고 `limitReached` 안내로 대체. 3개 미만이면 남은 자리를 **점선 "빈 슬롯" 카드**(두 번째/세 번째 씨앗)로 시각화 — 제약을 결핍이 아니라 **여백의 메시지**로 보여줌.
3. **최종 방어** (`app/add.tsx`): 만에 하나 추가 화면까지 가도 `addHabit()`이 `null`을 반환하면 Alert로 막고 저장하지 않음.

**반발 대응**: "무제한 원하는 사람"의 이탈은 **의도적으로 수용한 트레이드오프**다. 이 앱의 타겟은 "이미 여러 트래커에서 지쳐본 사람"이고, 그들에게 3개 제한은 반발이 아니라 안도다. 제약을 숨기지 않고 빈 슬롯·온보딩·스토어 카피("Just 3 habits. No more, no less.")로 **전면에 내세워** 기대를 사전 정렬한 것이 이탈을 줄이는 장치였다.

### Q2. 관용적 연속기록의 구체 규칙 — 며칠까지 봐주고 "안 끊김"을 어떻게 구현?

- **규칙**: 하루 빠짐 = **쉼표(breathing)**, 흐름 유지. **이틀 연속** 빠짐 = 흐름 종료(리셋).
- **구현**: 카운터를 저장하지 않고, 완료 로그에서 **오늘→과거로 역산**(최대 365일). `consecutiveMisses >= 2` 를 만나면 즉시 중단. 오늘만 비어 있으면 `isBreathingToday = true`로 카드에 "쉼표" 표시.
- **이중 트랙**: `currentFlowDays`(지금 흐름)와 `longestFlow`(역대 최장)를 분리 저장 개념으로 운영. 졸업·성장 단계 판정은 longestFlow 기준이라 **잠깐 끊겨도 키운 단계가 보존**된다.
- 성장 단계는 0/3/7/14/30/50일(씨앗→발아→떡잎→줄기→꽃봉오리→개화)로 흐름과 1:1 매핑. 50일 도달 시 **1회 자동 졸업 제안**.

### Q3. Expo 위젯에서 막힌 지점과 해결 / iOS 먼저·Android 보류 결정 근거?

- **막힌 지점**: ① JS↔Swift 메모리 단절(App Group + 자체 네이티브 모듈로 해결), ② 자정 경계 stale(타임라인 `.after(자정)` 정책으로 해결), ③ 위젯에서의 직접 체크(Android는 RemoteViews 낙관적 토글 + 포그라운드 동기화 큐, iOS는 정책상 탭→앱 진입으로 한정).
- **iOS 우선 근거 (헌법 9조)**: 네이티브 연동(위젯·햅틱·잠금화면 위젯)의 플랫폼 차이가 커서 **동시 완벽 대응은 MVP 일정을 확실히 파괴**한다. iOS로 위젯/알림/햅틱 코어를 먼저 검증한 뒤, 같은 데이터 동기화 패턴(App Group↔SharedPreferences)을 Android로 이식. Android는 "예외"가 아니라 코어가 검증된 뒤의 **자연스러운 졸업**으로 v1.1.0에 합류시켰고, v1.2.0에서 스토어 출시를 준비 중이다.
